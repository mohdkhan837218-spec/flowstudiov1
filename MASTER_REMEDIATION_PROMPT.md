# Flow Studio V2: Master Remediation Prompt

You are a senior Electron/Node.js security and reliability engineer. Audit and fix this repository completely. Do not stop at a report: inspect the code, implement focused fixes, run validation, and report exact files changed and remaining risks.

## Repository

- Electron desktop app using `main.js`, `preload.js`, `renderer/app.js`
- Automation engine under `engine/`
- Chromium/Puppeteer profiles under `profiles/`
- SQLite database under `data/`
- FFmpeg media processing and concurrent worker queues

## Required security fixes

1. Treat every IPC argument as untrusted. Validate the sender and reject calls from unexpected or navigated web contents.
2. Prevent path traversal for account IDs, Chrome profile names, ZIP entries, custom filenames, media input paths, media output paths, and download folders.
3. Restrict read/delete/scan/FFmpeg operations to explicitly configured media roots. Never allow arbitrary local file read, overwrite, or delete.
4. Allowlist Chrome profile names (`Default`, `Profile N`) and account IDs generated by the app.
5. Replace unsafe ZIP extraction with staged extraction. Accept only `accounts_meta.json` and `profiles/<valid-account-id>/Default/**`; reject absolute paths, `..`, unexpected files, and oversized archives.
6. Avoid storing or logging session cookies, proxy passwords, or other secrets in plaintext where possible. Do not expose them to the renderer unnecessarily.
7. Escape or avoid `innerHTML` for every account, email, prompt, error, filename, URL, and server-controlled value. Prefer `textContent` and DOM properties.

## Required reliability fixes

1. Make worker stop/restart awaitable. A new queue must not start until old browsers and workers are closed.
2. Prevent concurrent workers from claiming each other's native downloads. Use per-worker/task directories, download IDs, or a robust ownership marker instead of the first-new-file heuristic.
3. Bound captured network response memory and release buffers after successful/failed downloads.
4. Make DB initialization explicit before all IPC/database operations. Do not silently return empty state while initialization is pending.
5. Keep SQLite and legacy JSON state consistent, or make SQLite the single source of truth and migrate legacy JSON only once.
6. Make task state transitions idempotent. Stop/cancel must not mark unfinished tasks as completed or emit stale completion events after restart.
7. Ensure temporary FFmpeg files are always cleaned up in `finally` blocks and limit captured stderr/output memory.
8. Validate settings and numeric values such as concurrency, delays, limits, and filenames.

## Engineering rules

- Preserve existing UI and public behavior unless required for security or correctness.
- Make the smallest coherent changes; do not perform unrelated rewrites.
- Use existing libraries and patterns where possible.
- Do not disable Electron security features.
- Do not use `shell: true` for user-controlled values.
- Do not trust renderer-supplied account IDs or filesystem paths.
- Never use `git reset --hard` or revert unrelated user changes.
- Add focused tests or disposable validation scripts for traversal, unsafe ZIPs, IPC path rejection, filename sanitization, worker shutdown, and concurrent downloads.

## Validation checklist

Run all of the following after changes:

1. `node --check` for every JavaScript file.
2. A focused unit test for path/account/profile validation.
3. A ZIP traversal test using a disposable temporary directory.
4. A renderer search confirming account/email/prompt values are escaped or assigned with `textContent`.
5. A worker lifecycle test proving stop is awaited before restart.
6. A media test proving files outside configured download roots are rejected.
7. Review the final diff for unrelated changes and report residual risks honestly.

## Output format

Report:

- Critical findings fixed
- Files changed
- Tests/commands run and their results
- Remaining limitations or risks
- Any behavior that needs manual Google Flow/browser verification

Start by reading the owning implementation and nearby tests. State one falsifiable hypothesis and one cheap check before editing, then implement and validate the fixes instead of only describing them.
